# CheckInGo

**Teacher Attendance Tracking System**
*Simple Attendance. Better Monitoring.*

## Description

A beginner-friendly Flutter attendance tracking system for teachers.
Instead of writing attendance on paper, the teacher can record and monitor
student attendance (Present, Absent, Tardy) directly on a phone. Supabase can
store data in the cloud across a teacher's devices. Local demo access is only
available in debug builds; release builds require Supabase configuration.

## Technology

- Flutter
- Dart
- Supabase Auth and Postgres for cloud login and data
- `flutter_secure_storage` (Supabase sessions, PKCE values, and offline cache)
- `shared_preferences` (debug-only local demo storage)
- Basic `StatefulWidget` + `setState()` only (no Provider, Bloc, or GetX)

## Features

- Teacher Login
- Teacher registration with email and password
- Dashboard (today's Total Students, Present, Absent, Tardy)
- Student Management
- Student search by name, ID, course, or section
- Import a student roster from CSV
- Add Student
- Edit Student
- Delete Student (with confirmation)
- Add and remove teacher-owned sections from section dropdowns
- Take Attendance (choose date and section)
- Mark a whole section Present or Absent, then adjust individual students
- Present
- Absent
- Tardy
- Attendance Records (with date and section filter)
- Export a student roster or filtered attendance records as CSV
- Restore attendance CSV backups without deleting other sessions
- Encrypted on-device attendance drafts that sync after reconnecting
- Teacher password recovery by email
- Student Attendance Summary (counts, rate, and history)
- Attendance Statistics
- Local demo storage (SharedPreferences + JSON)
- Cloud storage with Supabase and per-teacher Row Level Security
- Logout (with confirmation)

## Attendance Rate

```
Attendance Rate = Present / Total Records x 100
```

Example: 18 Present out of 23 records = 78%.
**Tardy is not counted as Present** in this basic version.

## Supabase setup

The project includes a database migration at
`supabase/migrations/20261022000000_initial_schema.sql`. Create a Supabase
project in the Supabase Dashboard, open its SQL Editor, and run the contents of
that migration. Then run
`supabase/migrations/20261023000000_security_hardening.sql`. It adds database
field-size checks and revokes public/anonymous table privileges. The initial
migration creates the student and attendance tables and applies authenticated,
teacher-owned row security policies. Finally run
`supabase/migrations/20261023010000_section_management.sql` to create the
teacher-owned section list and protect sections that are still used by students
or attendance history. Run
`supabase/migrations/20261028010000_rename_sections.sql` to grant teachers
permission to rename their own sections; linked student and attendance records
are updated automatically. Finally run
`supabase/migrations/20261029000000_attendance_integrity.sql` to add an atomic,
teacher-scoped attendance save operation. This last migration is required for
cloud attendance saving and restoring.

#### Email/password registration

In Supabase **Authentication → Sign In / Providers**, enable the Email
provider and allow sign-ups. Keep email confirmation enabled so new teachers
must verify their address. The app's **New teacher? Create an account** link
registers a name, email, and password. Supabase sends the confirmation email;
the teacher can sign in after confirming it. Supabase returns no active session
until confirmation when that setting is enabled ([Supabase signup docs](https://supabase.com/docs/reference/dart/v1/auth-signup)).

The app's mobile email confirmation and password recovery callback is:

```text
io.supabase.checkingo://login-callback/
```

Add that exact URL under **Authentication → URL Configuration → Redirect
URLs** (sometimes shown as Additional Redirect URLs). The Android manifest and
iOS URL scheme are already configured in this project. Mobile auth redirects
must be allowed by Supabase and registered as an app deep link
([Supabase mobile deep-link docs](https://supabase.com/docs/guides/auth/native-mobile-deep-linking?platform=flutter)).
Password recovery uses the same app redirect. Keep the URL on the allow list,
then use **Forgot password?** on the sign-in page to receive a reset link.

Copy the Project URL and publishable key from the project's Connect panel and
use them in a local config file:

1. Copy `supabase_config.example.json` to `supabase_config.json`.
2. Replace the example values with the Project URL and publishable key. The
   local config file is ignored by Git.
3. Run the app with the config file:

```
flutter run --dart-define-from-file=supabase_config.json
```

Use only the publishable key in a Flutter app. Never include a Supabase secret
or service-role key. With Supabase configured, the login screen supports
teacher email/password registration and sign-in, and data is scoped to the
authenticated account. Public registration currently accepts any verified
email; it does not verify that the person is a Northeastern College teacher.
Before a public release, use an institution-approved signup policy (for
example, teacher invites or a verified school email domain) if only school
staff should get accounts. Row Level Security still scopes each account to
its own records.

Without those settings, debug builds can use the local demo. Release builds
show a setup error and cannot enter local mode.

No live Supabase project is included in this ZIP. A Supabase account is needed
to create one and provide its Project URL and publishable key.

### Importing a student roster

From the **Students** page, choose **Import CSV roster** and select a CSV file.
The file must have `student_id`, `name`, `course`, and `section` columns. Column
order does not matter; common alternatives such as `student number`, `full
name`, and `program` are accepted. Existing or repeated student IDs are skipped
and reported before import. A starter file is in
`templates/student_roster_template.csv`.

Keep student IDs formatted as text in spreadsheet software so leading zeros are
preserved when exporting to CSV.

### Backups and offline attendance

On the Students page, use the download button to export the roster. On
Attendance Records, use **Export CSV** to save the currently filtered rows, or
**Restore CSV** to merge a backup. Restore checks student IDs against the
current teacher's roster, previews skipped rows, and asks before importing.
It updates only matching student/date/section attendance rows.

After the teacher has loaded the roster and records online, the app keeps an
encrypted local cache. If the connection drops while taking attendance, it
saves that session to encrypted device storage and retries when attendance is
loaded again online. Offline drafts are device-specific; keep CSV backups for
long-term recovery or moving to another device.

### Applying the latest database migration

Open the **CheckInGo** Supabase project that already contains the
`checkingo_students`, `checkingo_sections`, and `checkingo_attendance` tables.
In **SQL Editor**, choose **New query**, paste the complete contents of
`supabase/migrations/20261029000000_attendance_integrity.sql`, and press
**Run**. Wait for “Success” before running the app. Do not paste this migration
into `initial_schema.sql`; it is a separate follow-up migration. If those three
tables are missing, first select the correct Supabase project and apply the
previous migrations in timestamp order.

3. Run the app in debug demo mode (with an emulator or phone connected):

```
flutter run
```

4. (Optional) Run the tests:

```
flutter test
```

## Basic Workflow

Login -> Dashboard -> Students -> Take Attendance -> Save Attendance ->
Attendance Records -> Student Attendance -> Logout

## Notes

- Saving attendance for a date and section that already exists asks the teacher
  if they want to update it, so there are no duplicate records.
- Deleting a student also deletes that student's attendance records.
- Editing a student's ID or name also updates their old attendance records.
- QR check-in is not included yet: a teacher-generated code needs a student-
  facing check-in page and a server-validated, short-lived session token. A
  code by itself would not verify who scanned it.

## Release preparation

The project is prepared to require Supabase in release builds, keep the
Supabase session in Android secure storage, block cleartext HTTP, exclude app
data from Android backup/transfer, and refuse release signing with a debug
certificate. These changes reduce risk but do not guarantee approval by any
app store.

Before publishing:

1. Choose the school's final unique Android application ID. The current
   `com.example.check_in_go` is a development placeholder. Change it in
   `android/app/build.gradle.kts` before the first public release; changing it
   later creates a different app listing. Update both `namespace` and
   `applicationId` together.
2. In Supabase, use teacher invitations or another institution-approved signup
   policy if accounts must be limited to Northeastern College staff. If public
   registration is enabled, verify the email/domain policy before release. Run
   all five SQL migration files in order and confirm each table still has
   row-level security enabled.
3. Make an institution-approved privacy policy that explains what student and
   attendance data is collected, why it is used, who can see it, how long it is
   retained, how deletion requests work, and the school's contact. Put its URL
   in the store listing and make the policy reachable from the app before
   release.
4. Create and securely back up a private signing key. From the project folder,
   run:

   ```powershell
   keytool -genkeypair -v -keystore android/app/upload-keystore.jks -keyalg RSA -keysize 2048 -validity 10000 -alias checkingo
   Copy-Item android/key.properties.example android/key.properties
   ```

   Edit `android/key.properties` with the key alias and passwords entered when
   creating the key. Keep both that file and `upload-keystore.jks` private and
   backed up; losing the key can prevent updates to the same app listing.
5. Set the real Supabase URL and publishable key in the ignored
   `supabase_config.json` file, then build a signed Android App Bundle:

   ```powershell
   flutter build appbundle --release --dart-define-from-file=supabase_config.json
   ```

   The output is `build/app/outputs/bundle/release/app-release.aab`. The
   Android build targets at least API 36; ensure the Android SDK platform and
   build tools are installed.
6. Test the signed release on real devices with teacher accounts, verify that
   two accounts cannot see each other's records, and check the final store
   listing, screenshots, support contact, and data-safety/privacy disclosures.

Store requirements change and differ by platform. The final application ID,
school privacy-policy details, store disclosures, and the store's review are
still required for publication.
